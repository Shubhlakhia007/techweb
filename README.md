# techweb

> **Find your people. Build what's next.**

techweb is a skill-based team formation platform for hackathons and CTFs. It connects builders by their actual skills, shows teams what roles they're still missing, and makes it easy for individuals to discover competitions worth joining.

## What the App Does

| User Goal | How techweb Helps |
|---|---|
| Find a hackathon or CTF to enter | Browse the events list with filters for type, mode, and required skills |
| Build a team with complementary skills | Create a team under any event; the platform surfaces skill gaps and recommends candidates |
| Join a team that needs your skills | Discover teams and see instantly whether your profile fills a gap |
| Share who you are as a builder | Build a profile with skills, proficiency, experience level, and work links |

## Tech Stack

| Layer | Technology | Why |
|---|---|---|
| Framework | **Next.js 16 (App Router)** | Server components = zero-JS pages by default; RSC streaming; file-system routing |
| UI | **React 19** | Concurrent mode; Server Actions for form mutations |
| Language | **TypeScript 5** | End-to-end type safety across API ↔ DB ↔ UI |
| Styling | **Vanilla CSS** (single `globals.css`) | No runtime overhead; full control; zero dependencies |
| ORM | **Prisma 6** | Type-safe DB queries; schema migrations; supports SQLite locally and PostgreSQL in production |
| Database (local) | **SQLite** (`prisma/dev.db`) | Zero-config, file-based, instant setup |
| Database (production) | **Neon PostgreSQL** | Serverless Postgres with connection pooling; free tier available |
| Auth | **Custom session tokens** via Node.js `crypto` | No third-party auth service dependency; SHA-256 hashed tokens stored in DB |
| Google OAuth | **PKCE + ID token** via `jose` | Follows the OpenID Connect standard; no additional Google SDK |
| Hosting | **Vercel** | Free hobby tier; serverless functions; automatic preview deployments |

## Architecture Overview

```
Browser
  │
  │  (1) Full-page navigation — HTML + CSS only, zero client JS for page loads
  ▼
Next.js App Router (Vercel Serverless Functions)
  │
  ├── Server Components (RSC)          ← Runs on server; no JS shipped to browser
  │     • Fetch from Prisma directly
  │     • currentUser() cached per-request via React.cache()
  │     • Render HTML with streamed Suspense
  │
  ├── Client Components ('use client') ← Only for interactivity
  │     • Navigation (pathname detection, mobile menu)
  │     • Forms (AuthForm, ProfileForm, EventForm)
  │
  └── API Route Handlers (/api/*)      ← JSON-only, same-origin enforced
        • Validate input with lib/http.ts helpers
        • Call lib/auth.ts for session management
        • Call Prisma for DB mutations
        │
        ▼
      Prisma ORM
        │
        ├── Local: SQLite file (dev.db)
        └── Production: Neon PostgreSQL (pooled + direct URLs)
```

### Key Design Choices

**Server-first rendering.** Every page is a React Server Component by default. Prisma queries run directly inside page components — no extra API call needed for initial render. This gives fast first-contentful-paint with no client-side waterfall.

**Single CSS file.** All styles live in `globals.css`. No CSS-in-JS, no Tailwind runtime, no styled-components. The browser caches this one file aggressively.

**`React.cache()` for session deduplication.** `currentUser()` is wrapped in `cache()`. The root layout and any page that calls it within the same request share one DB round-trip.

**No third-party auth library.** Sessions are SHA-256-hashed random tokens stored in the `Session` table. `httpOnly` + `SameSite=lax` cookies prevent XSS/CSRF. `timingSafeEqual` prevents timing attacks on password comparison.

## How the Web Works — End to End

### Request Lifecycle

```
User types URL or clicks a Link
         │
         ▼
  Next.js Router (App Router)
         │
         ├── Static segment match → finds the right page.tsx
         ├── Dynamic segment → [eventId], [teamId] extracted
         │
         ▼
  Root Layout (layout.tsx) runs first
         │
         ├── currentUser() → reads session cookie → DB lookup (cached)
         ├── <Navigation signedIn={...} /> rendered (client boundary)
         └── {children} → the matched page.tsx
                 │
                 ▼
         Page Server Component
                 │
                 ├── Direct Prisma queries (parallel with Promise.all)
                 ├── Returns HTML → streamed to browser
                 └── Interactive parts use 'use client' child components
                            │
                            ▼
                     Browser receives HTML + CSS
                            │
                            └── React hydrates only the client boundaries
                                (Navigation, Forms) — not the whole page
```

### Authentication Flow

#### Email / Password

```
Register / Login page (client component)
  └── User fills form → fetch POST /api/auth
          │
          ▼
     /api/auth/route.ts
          ├── sameOrigin() check (rejects cross-origin fetch)
          ├── Validate email format + password length
          ├── Register: hash password with scrypt(salt, 64 bytes)
          │           create User row
          ├── Login:   find user → verifyPassword with timingSafeEqual
          └── startSession()
                  ├── randomBytes(32) → raw token
                  ├── SHA-256 hash → stored in Session table
                  ├── Original token → set in httpOnly cookie (7 days)
                  └── Response: { ok: true }
```

#### Google OAuth (PKCE flow)

```
User clicks "Sign in with Google"
  └── fetch GET /api/auth/google
          ├── Generate code_verifier (random 32 bytes, base64url)
          ├── Compute code_challenge = SHA-256(verifier), base64url
          ├── Generate nonce (random 32 bytes)
          ├── Store verifier + nonce in signed cookie (techweb_google_flow)
          └── Redirect to Google with response_type=code, PKCE params
                  │
                  ▼
           Google authenticates user
                  │
                  ▼
     GET /api/auth/google/callback?code=...
          ├── Read verifier + nonce from cookie
          ├── Exchange code for tokens (POST to Google token endpoint)
          ├── Verify ID token: signature (JWKS), iss, aud, nonce, exp, email_verified
          ├── googleAccount(): find or create User row by googleId
          └── startSession() → set cookie → redirect to /profile
```

### Skill Matching Engine

The matching engine (`src/lib/matching.ts`) is **pure TypeScript** — no AI, no external service. It runs on every team detail page load.

```
Team detail page loads
  └── Prisma fetches: team members + their skills, event required skills, all users
          │
          ▼
  computeTeamVector(members)
  → Map<skillId, memberCount>
  → e.g. { "react": 2, "python": 1 }
          │
          ▼
  computeGapVector(teamVector, requiredSkills)
  → Skills where coverage < minCount
  → e.g. { "docker": 1, "security": 2 }
          │
          ▼
  rankCandidates(allUsers, currentMemberIds, gapVector, requiredSkills)
  → Filter out existing members
  → For each candidate: count their skills that appear in gapVector
  → Sort descending by score
  → Return top candidates with matchingSkills array
```

**Result:** The UI shows "people who fill your gaps" — transparent, fast, and explainable.

### Eligibility Checking

Before a user joins a team, two checks run in `src/lib/eligibility.ts`:

| Check | Logic |
|---|---|
| **Team capacity** | `count >= teamSizeMax` → hard fail |
| **Event mode preference** | If user set "online only" and event is offline → fail |
| **Region restriction** | If event has `regionRestriction`, user's `location` field must contain that region token |
| **Diversity rule** | If event has `diversityRuleText` → shown as manual check (cannot be auto-verified) |
| **Travel / Availability** | Always shown as manual for offline/hybrid events |

`eligible: false` blocks the join API. Manual items are displayed to the user but don't block joining.

## Database Schema

```
User ──< UserSkill >── Skill
 │
 ├──< Session              (hashed tokens)
 ├──< ProfileLink          (custom work/social links)
 ├──< createdEvents        (Event)
 │       └──< EventRequiredSkill >── Skill
 │       └──< EventRound           (multi-round events)
 │       └──< Team
 │               └──< TeamMember >── User
 └──< createdTeams         (Team)
```

### Key Models

| Model | Purpose |
|---|---|
| `User` | Profile, credentials, preferences, social links |
| `Session` | SHA-256 hashed session token + expiry (7 days) |
| `Skill` | Global skill catalogue (seeded, user-extensible) |
| `UserSkill` | Join table: user ↔ skill with proficiency 1–5 |
| `Event` | Hackathon or CTF with type, mode, team size limits, rounds |
| `EventRequiredSkill` | Which skills an event needs and how many people |
| `EventRound` | Named rounds (e.g. "Online qualifier", "In-person final") |
| `Team` | Group formed under an event |
| `TeamMember` | User in a team with role (leader/member) |
| `ProfileLink` | Freeform URL + label (GitHub, Devpost, portfolio, etc.) |

## API Routes Reference

All routes return `application/json`. All mutation routes require `Content-Type: application/json` and enforce same-origin.

| Method | Path | Auth | Description |
|---|---|---|---|
| `POST` | `/api/auth` | No | `register`, `login`, `logout` |
| `GET` | `/api/auth/google` | No | Start PKCE OAuth flow → redirect to Google |
| `GET` | `/api/auth/google/callback` | No | Exchange code, verify ID token, start session |
| `PATCH` | `/api/profile` | Required | Update name, bio, skills, links, preferences |
| `GET` | `/api/skills` | No | List all skills (for pickers) |
| `POST` | `/api/events` | Required | Create a new event |
| `POST` | `/api/teams` | Required | Create a team under an event |
| `POST` | `/api/teams/[teamId]/join` | Required | Join a team (runs eligibility check first) |
| `GET` | `/api/teams/[teamId]/eligibility` | Required | Check join eligibility for current user |
| `GET` | `/api/teams/[teamId]/recommendations` | Required | Ranked candidates who fill skill gaps |
| `GET` | `/api/users` | Required | Returns `{ id, name }` for the current user |

## Deployment Pipeline (Vercel + Neon)

### How the dual-schema setup works

Locally, Prisma uses **SQLite** (no server needed). On Vercel, it uses **Neon PostgreSQL**. The `scripts/neon-schema.mjs` script automatically transforms the SQLite schema into a PostgreSQL-compatible one before each production build.

```
prisma/schema.prisma          ← Source of truth (SQLite syntax)
        │
        │  npm run db:neon:prepare
        ▼
prisma/neon/schema.prisma     ← PostgreSQL version (git-ignored, auto-generated)
        │
        │  prisma migrate deploy
        ▼
Neon PostgreSQL               ← Production database
```

### Step-by-step Vercel deployment

1. **Create a Neon project** → copy the pooled and direct connection strings.

2. **Import repo into Vercel** → set Root Directory to the repo folder.
   - Framework: Next.js
   - Build command is set in `vercel.json`: `npm run build:vercel`

3. **Add these environment variables in Vercel** (Production):
   ```
   DATABASE_URL   = neon pooled connection string
   DIRECT_URL     = neon direct connection string
   APP_URL        = https://your-app.vercel.app
   GOOGLE_CLIENT_ID     = (optional, for Google sign-in)
   GOOGLE_CLIENT_SECRET = (optional, for Google sign-in)
   ```

4. **Deploy.** The build command runs:
   ```bash
   node scripts/neon-schema.mjs          # Generate PostgreSQL schema
   prisma generate --schema prisma/neon/schema.prisma
   prisma migrate deploy --schema prisma/neon/schema.prisma
   next build
   ```

5. **Verify** by signing up, creating an event, and joining a team.

> **Preview deployments:** Use a separate Neon branch with its own `DATABASE_URL`/`DIRECT_URL`. Never point preview builds at the production database.

## Future Roadmap

### Google OAuth *(infrastructure already in place)*

The full PKCE + ID token verification flow is implemented in `src/lib/google.ts` and `src/app/api/auth/google/`. It is gated behind environment variables. To enable:

1. Create a Google Cloud OAuth web client.
2. Register the callback URI: `https://your-app.vercel.app/api/auth/google/callback`
3. Add `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `APP_URL` to Vercel.
4. Redeploy — the sign-in button becomes active automatically.

Account linking rules:
- A Google account matches only by `googleId` (the `sub` claim), not by email alone.
- Existing password accounts must sign in first, then connect Google from their profile page.

## Security Design Decisions

| Concern | Decision |
|---|---|
| **Password storage** | `scrypt` with 16-byte random salt; 64-byte derived key |
| **Timing attacks** | `timingSafeEqual` on password comparison |
| **Session tokens** | 32 random bytes; SHA-256 hash stored in DB; raw token in cookie only |
| **Cookie flags** | `httpOnly`, `SameSite=lax`, `Secure` in production |
| **CSRF** | Same-origin check on all mutation APIs (`sameOrigin()`) + `SameSite=lax` |
| **XSS** | React escapes output by default; no `dangerouslySetInnerHTML` |
| **Google OAuth** | PKCE prevents code interception; nonce prevents replay; `email_verified` must be true |
| **Account linking** | Email alone never links accounts; `googleId` (`sub`) is the sole identifier |
| **Open redirect** | `safeDestination()` allowlists redirect paths after OAuth |
| **Input validation** | All API inputs validated with `text()`, `choice()`, `integer()` before DB writes |
